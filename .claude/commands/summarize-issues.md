# ISUCON 改善課題の Issue 化

あなたは ISUCON の参加者です。**スコアを上げること**が唯一の目的です。
このリポジトリを解析し、スコア向上のために解決すべき課題を洗い出して、
**課題1つ = GitHub Issue 1つ**として作成し、それらを束ねる **Dashboard Issue** を作成してください。

**手順は必ずこの順で進める。マニュアル読解（§0）を飛ばしてコード解析に入ってはいけない。**
マニュアルを読まずに出した課題は、禁止された変更・整合性チェック違反・加点されない改善を含みやすく、当日そのまま事故になる。

当日の競技時間を削らないため、**アプリコードを読む作業（§2-3）と Issue を書く作業（§4）はサブエージェントで並列化する**。
ただし**判断は直列で1箇所に集める**（§0 マニュアル読解 / §2-1 共通下地 / §3 統合と優先度付け / §6 Dashboard）。
並列化は速度のためであって、判断を分散させるためではない。

追加指示（あれば優先して従う）: $ARGUMENTS

- `--dry-run` が渡された場合は Issue を作成せず、作成予定の内容を一覧で出力して終了する。
- `--serial` が渡された場合、またはサブエージェントを起動できない場合は、**並列化せず1つのコンテキストで同じ手順を順番に実行する**（判断基準は一切変えない）。
- **§0 のマニュアル読解は必須。省略する手段は無い。** マニュアルが手に入らない場合は Issue を作らず中断する。
- 絞り込み（例: `db only`）があれば、その領域を重点的に扱う。

## 実行の全体像

```
§0 マニュアル読解         直列（本体が全文を読む）→ /tmp/isucon-manual-notes.md
§1 前提固め               1-1 gh 疎通・既存Issue（§0 と並行可） / 1-2 ラベル8件（§0 完了後）
§2-1 共通下地             直列（DDL・設定・計測上位・ルーティング表）→ /tmp/isucon-facts.md
§2-2 構成・設定の所見     直列（下地を見れば分かるもの。infra / DB設定 / 計測整備）
§2-3 アプリコードのスキャン 並列3〜4（**エンドポイント単位の縦割り**）→ 所見だけを返す
§3 統合                   直列（重複排除・除外・優先度・ID付与）→ /tmp/isucon-issue-plan.md
§4 Issue 執筆＋作成       並列（1体 = 1 Issue、同時最大5）
§5 作成結果の照合         直列（欠けを検出して1回リトライ）
§6 Dashboard Issue        直列
§7 最終報告
```

**バリアは3つある。ここを飛ばすと精度が落ちる。**
- §0 の完了 → メモが揃うまで §2 を始めない（サブエージェントはメモしか制約を知らない）
- §2-1 の完了 → 下地が揃うまで §2-3 を起動しない（下地なしのスキャナは index 不足を判定できない）
- §4 の完了 → 全 ID に Issue 番号が付くまで §6 に進まない

## 0. マニュアル読解（最初に必ずやる）

**当日マニュアル**（競技のルール）と**アプリケーションマニュアル**（アプリの仕様）を先に読み切る。
マニュアルは必ずレポジトリ内にあるものを参照すること(外部webページから取得することはしない)
- もしリポジトリ内に二つのマニュアルが無い場合は、その旨をユーザーに伝えて中断する。
ここで抽出した制約が、以降すべての Issue の判断基準になる。

**この節は並列化しない。** 本体のコンテキストで2文書を全文読み切る。

### 0-1. マニュアルを探す

引数で場所が指定されていればそれを使う。指定が無ければ次を順に探す。

```sh
# リポジトリ内のマニュアル候補
ls -la
find . -maxdepth 3 -iname "*manual*" -o -iname "*regulation*" -o -iname "*rule*" \
  -o -iname "*spec*" -o -iname "*isucon*.md" | grep -v node_modules
ls -la docs/ manual/ 2>/dev/null
```

- リポジトリ内の `README.md` / `docs/**` / `*.md` / PDF / HTML
- **どこにも見つからない場合は、勝手に一般論で進めない。**
  「当日マニュアルとアプリケーションマニュアルの場所（パス）を教えてください」と伝えて**中断する**。
  マニュアル無しで Issue を作ることは**しない**。

### 0-2. 当日マニュアルから抽出する（ルール系）

読み飛ばさず、次の項目を**引用付きで**書き出す。1つでも不明なら「マニュアルに記載なし」と明記する。

- **スコア計算式** — 何が加点され、何が減点されるか。エンドポイントごとに重みが違うか
- **失格・再試行条件** — 整合性チェックの失敗、タイムアウト、エラー率の上限
- **変更禁止事項** — 触ってはいけないファイル・パス・ポート・レスポンス形式・外部サービス
- **追加してよいミドルウェア** — Redis / memcached / 別 DB の可否、インストール可否
- **サーバ構成** — 台数、スペック、どの台に何が載っているか、ネットワークの制約
- **ベンチマーカーの実行方法と挙動** — 並列度、実行時間、ポーリングするか、遅ければ待つか
- **再起動試験の条件** — 何を再起動され、どこまでの復旧が要求されるか
- **計測ツールの使用可否**、ログ出力に関する制約

### 0-3. アプリケーションマニュアルから抽出する（仕様系）

- **エンドポイント一覧**と、それぞれが返すべき内容・ステータスコード
- **整合性チェックの条件** — どのデータが、いつ、どの粒度で正しくなければならないか
- **キャッシュの可否と許容 stale** — 「N 秒古くてよい」「即時反映が必要」の線引き
- **画面ごとの表示要件**（並び順、件数、ページング、リアルタイム性）
- **ユーザー種別・権限**、認証方式（セッション、トークン）
- **外部 API・外部コマンド**への依存と、その制約（レート制限、置き換え可否）
- **初期データの規模**と、`/initialize` に要求される挙動・制限時間

### 0-4. 抽出結果をメモにする（以降のすべての入力）

抽出結果を `/tmp/isucon-manual-notes.md` に書き出す。

**このメモは単なる作業メモではない。** §2-3 のスキャナと §4 の writer は
**マニュアル原文を一切読まず、このメモだけを制約として使う**。よって次を必須とする。

- 抽出項目ごとに**逐語引用 + 出典（節名・見出し）**を載せる。要約だけにしない
- §0-2 / §0-3 の項目を**1つも省かない**。記述が無いものは「マニュアルに記載なし」と明記する
- §0-5 で確定した判断を**メモの先頭に「結論」として書く**（加点されない領域 / キャッシュ可否 /
  禁止されている変更 / 割のいい領域）
- 本体が原文をコンテキストに持っていても省略しない。**メモに書いていない制約は下流に伝わらない**

このメモの要点は Dashboard Issue の「マニュアル要点」節にそのまま載せる。

### 0-5. マニュアルから直接導く判断

コード解析に入る前に、次を確定させる。

- **加点されないエンドポイント** — 速くしても意味がない。Issue にしない（または優先度を下げる）
- **キャッシュしてよいリソース / だめなリソース** — キャッシュ系 Issue はここに必ず紐づける
- **禁止されている変更** — 該当する改善案は**最初から候補から外す**
- **スコア計算式から見て最も割のいい領域** — 優先度付けの土台にする

**マニュアルの記述と矛盾する Issue は作らない。** 判断できない場合は Issue 本文に「マニュアル要確認」と書く。

## 1. 前提固め

### 1-1. 読み取りだけの確認（§0 と並行に投げてよい）

副作用が無いので、§0 のファイル読み込みと**同じメッセージで同時に投げてよい**。

```sh
gh auth status || exit 1
gh repo view --json nameWithOwner,url
gh issue list --state open --limit 100 --json number,title,labels
```

- `gh` が未認証なら、その旨をユーザーに伝えて中断する（勝手に認証を試みない）。
- 既存 Issue の一覧（番号・タイトル・ラベル）は **§3 の重複判定で使う**ので必ず保持する。

### 1-2. ラベル整備（**§0 が通ってから**・書き込みなので前倒ししない）

**マニュアルが見つからず中断する場合、リポジトリにも GitHub にも何も書き込まないこと。**
よってラベル作成は §0 の完了後に1回の Bash で行う。`--force` で冪等。

## 2. リポジトリ解析（推測ではなく実物を読む）

**割り方の原則: 層（app / db / infra）で割らず、縦（エンドポイント）で割る。**

- 層で割ると分量が釣り合わない。実測（ISUCON13）で Go は 2,272行だが、DDL は grep で 27行、
  my.cnf は 149行、Makefile 類は 103行。**並列の所要時間は一番長い枝（アプリコード）で決まる**ので、
  設定系を別エージェントに出しても短縮はほぼゼロ。
- そして層で割ると精度が落ちる。ISUCON で一番効く所見は
  **`ハンドラ → 発行される SQL → テーブルの index → nginx の扱い` と縦に貫くもの**で、
  DDL を知らない担当は「N+1」しか言えず、呼び出し元を知らない担当は index の必要性を判断できない。
- よって: **安くて全員に必要な情報は本体が先に読んで下地にし（§2-1）、
  設定・構成の所見も本体が出し（§2-2）、fan-out はアプリコードだけをエンドポイント単位で行う（§2-3）。**

読みながら、§0 で抽出した仕様（整合性チェックの条件、キャッシュ可否、加点対象）と**コードの実装を突き合わせる**。
存在しないものは無理に触れない。

### 2-1. 共通下地を作る（直列・本体が読む）

**合計で千行を超えないように読む。** 結果を `/tmp/isucon-facts.md` に書き出し、全スキャナに渡す。

```sh
# 計測結果（あれば最重要の根拠）— 上位だけ見る
head -40 alp_analysis.txt pt_query_digest_analysis.txt mysqldumpslow_analysis.txt 2>/dev/null

# DDL だけを見る（初期データ dump は絶対に開かない）
wc -l **/*.sql 2>/dev/null
grep -rn 'CREATE TABLE\|CREATE INDEX\|ADD INDEX\|UNIQUE KEY\|PRIMARY KEY\|KEY `' --include='*.sql' .

# ルーティング表（handler の入口を押さえる）
grep -rn 'e\.GET(\|e\.POST(\|e\.PUT(\|e\.DELETE(\|HandleFunc(\|router\.' --include='*.go' webapp/
```

読むもの（これ以外に手を広げない）:

- **計測結果**: `alp_analysis.txt`, `pt_query_digest_analysis.txt`, `mysqldumpslow_analysis.txt`、ベンチ結果ログの**上位のみ**
- **DDL**: 上の grep 結果だけ。`wc -l` が数千行を超える SQL は INSERT の塊なので**開かない**
- **DB 設定**: `mysql/**`（`pull.sh` が `isucondb:/etc/mysql/` を落としてくる先）、`my.cnf`, `**/*.cnf`
- **Web サーバ**: `nginx/**`（`pull.sh` が `isuconapp:/etc/nginx/` を落としてくる先）のうち
  **実際に効いている conf のみ**（`nginx.conf` と `sites-*` / `conf.d`）。
  `mime.types` / `fastcgi_params` / `*.default` は開かない
- **ミドルウェア/OS**: systemd unit, `sysctl`, `ulimit`, Redis/memcached の有無
- **運用**: `Makefile`, `deploy.sh`, `pull.sh`, `install_tools.sh`, `.github/workflows/**`
- **ドキュメント**: `README.md`, `CLAUDE.md`

`/tmp/isucon-facts.md` に必ず載せるもの:

| 節 | 内容 |
|---|---|
| 計測上位 | エンドポイント / クエリごとに sum・count・avg。**無い場合は「未計測」と明記** |
| テーブル一覧 | 1行1テーブル。列と**既存 index**（複合 index は列順まで） |
| MySQL 設定 | 効いている値（buffer pool、`innodb_flush_log_at_trx_commit`、`sync_binlog`、`max_connections`、スロークエリ設定） |
| nginx 設定 | 効いている値（`worker_processes`、`worker_connections`、`keepalive`、`gzip`、静的配信、ログフォーマット） |
| ルーティング表 | メソッド + パス + handler 名 + `file:line` |
| 構成 | 台数と役割（メモから）、`Makefile` / CI で何が起きるか |
| 未pull | `webapp/**` などが未取得なら**その旨を明記**（`sh ./pull.sh` が必要） |

計測結果ファイルが存在する場合は、以降**必ずその数値を根拠として引用**する（例: `GET /api/isu/:id/graph` が sum 42.5s で全体の 38%）。
存在しない場合は「まず計測する」課題（`make nginx/alp` / `make mysql/pt-query-digest` の実行、`/analyze` コメント運用）を**最優先の所見**として立てる。

### 2-2. 構成・設定の所見を出す（直列・本体が下地から出す）

下地を1回見れば判断できるものは、**並列化せず本体がここで所見にする**（読む量が小さく、割る意味がない）。

**インフラ / ミドルウェア**
- nginx: `keepalive`（upstream 含む）、`worker_processes auto`、`worker_connections`、`gzip`/`gzip_static`、`sendfile`、静的配信、`open_file_cache`、`proxy_buffering`
- 静的ファイル・API レスポンスのキャッシュ（`expires`、`Cache-Control`、`proxy_cache`）
- ベンチ中の**ログ出力停止**（nginx access_log off / MySQL slow log off）※計測時は逆に有効化
- 複数台構成の役割分担（app / db / 内部 API の振り分け、nginx でのロードバランス）
- systemd の制限（`LimitNOFILE`）、`sysctl`（`somaxconn`, `tcp_tw_reuse`）、ファイルディスクリプタ
- unix domain socket 化（nginx ↔ app、app ↔ MySQL）
- 不要プロセスの停止、メモリ・CPU 使用状況の確認

**DB の設定・構成**（個別クエリの話は §2-3 に任せる）
- MySQL パラメータ（buffer pool、`innodb_flush_log_at_trx_commit=0/2`、`sync_binlog=0`、binlog 無効化）
- テーブル設計の大きな話（非正規化、集計カラムの持ち回り、不要カラムの分離、型の縮小）
- DB を別ホストへ分離 / 逆に同一ホストへ集約（構成に応じて）
- Redis 等への移し替え（セッション、カウンタ、ランキング）※メモで許可されている場合のみ

**計測・運用（スコアを上げるための土台）**
- alp / pt-query-digest / スロークエリの計測フロー整備とログローテート
- ベンチ実行 → 計測 → 修正のサイクル短縮（`make` ターゲット、`deploy.sh`、CI）
- ベンチ本番時に計測を切る/戻す手順の明文化
- pprof / メトリクスの導入

所見は §2-5 のフォーマットで書く（スキャナの返り値と同じ形にして、§3 で同じプールに入れる）。

### 2-3. アプリコードのスキャン（並列3〜4・縦割り）

**割り当て方**

1. 計測結果があれば、**alp / スロークエリの上位から、担当の合計 sum が均等になるように**
   エンドポイントを3〜4グループに分ける（重いものを別担当に散らす）
2. 計測結果が無ければ、ルーティング表を**機能単位**で分ける（例: ユーザー系 / 配信系 / コメント系 / 統計系）
3. 絞り込み条件（例: `db only`）があれば、担当数を減らして重点領域に寄せる

**各スキャナがやること（縦に貫く）**

担当エンドポイントの handler を起点に、次を順に追う。

```
handler（file:line）
  → 発行される SQL（ループ内か / 1リクエストで何回か）
  → 使われるテーブルの既存 index（facts のテーブル一覧を参照。無ければ「index 不足」と判定できる）
  → レスポンスの組み立て（N+1 / 重複計算 / JSON 量）
  → nginx 側の扱い（静的配信・キャッシュ可能か。facts の nginx 設定を参照）
  → キャッシュ可否（マニュアルメモを参照。整合性チェックに触れないか）
```

- **担当外のエンドポイントは見ない**（重複所見を防ぐ）。
  ただし担当内から呼ばれる共通ヘルパ（`fillLivestreamResponse` のような関数）は見てよい。
  共通ヘルパの所見は複数担当が挙げうるので、§3 で畳む前提で構わない。
- 所見の**カテゴリは縦に追った結果で選ぶ**。index が無いことが原因なら `db`、
  ループの構造が原因なら `app`、静的配信に落とせるなら `infra`。担当名で決めない。
- 巨大なハンドラファイルは `grep -n` で SQL 発行箇所とループを先に特定し、**その周辺だけ Read** する。

**観点（アプリケーションコード）**
- N+1 クエリ（ループ内クエリ、関連取得の逐次実行）→ JOIN / IN 一括取得 / アプリ側 JOIN
- 不要なクエリ・全件取得（`SELECT *`、LIMIT 無し、COUNT の多用）
- 同一リクエスト内・リクエスト間の重複計算 → メモリキャッシュ / sync.Once / TTL キャッシュ
- 重い処理の同期実行 → 非同期化・バッチ化・遅延書き込み（bulk insert、キュー）
- ループ内 INSERT/UPDATE → バルク化、トランザクションまとめ
- パスワードハッシュ・画像変換などの CPU 重処理 → コスト調整・キャッシュ・事前生成
- 画像/ファイルを DB から配信 → 静的ファイル化して nginx 配信 or キャッシュ
- DB コネクションプール設定（`SetMaxOpenConns` / `SetMaxIdleConns` / `SetConnMaxLifetime`）
- JSON エンコード・ログ出力・デバッグログのオーバーヘッド
- ロック競合・排他制御の粒度、無駄な `sleep` / リトライ
- `/initialize` の初期化コストと整合性（キャッシュのクリア漏れは失格リスク）

**観点（担当エンドポイントに紐づく DB の話）**
- 欠落 INDEX（WHERE / ORDER BY / JOIN キー、複合 INDEX の順序、カバリング INDEX）
- 効いていない INDEX（関数適用、型不一致、前方一致でない LIKE）
- スロークエリ上位の個別チューニング（`EXPLAIN` 結果を根拠にする）
- 不要トランザクション（参照だけの `BeginTx`）、分離レベル

### 2-4. スキャナ共通の前置き（プロンプト先頭にそのまま貼る）

```
あなたは ISUCON 参加チームの調査担当です。目的はスコア向上のための課題整理です。

最初に必ず次の2つを Read する:
- /tmp/isucon-manual-notes.md … マニュアルから抽出した制約。ここに反する提案はしない
- /tmp/isucon-facts.md      … テーブルと既存 index、MySQL/nginx の設定値、計測上位、ルーティング表

必ず守ること:
- 推測でパスや行番号を書かない。出すパスは Read / Grep / Glob で実在を確認したものだけにする
- テーブルの index は facts を参照して判断する（「index が無い」は facts で確認してから言う）
- 外部 Web を参照しない（WebFetch / WebSearch を使わない）。参照はリポジトリ内のファイルのみ
- 初期データの SQL dump は開かない（数万行あるため。必要なら grep で DDL だけ見る）
- 該当箇所を示せない一般論は返さない

禁止:
- GitHub Issue の作成・編集・クローズ、ラベルの作成
- アプリケーションコードや設定ファイルの修正（この作業は調査のみ）
- 他のエージェント（Agent / Task）の起動
- 優先度（priority:*）の決定 — 優先度は全体を見る担当が横断で決めるので、あなたは付けない
- 担当外のエンドポイントの調査（共通ヘルパを除く）

返り値は指定されたフォーマットのブロックの連結だけにする。前置き・感想・要約は書かない。
```

あわせて渡すもの:

- 担当エンドポイント一覧（メソッド + パス + handler 名 + `file:line`、計測上位の数値つき）
- §1 で取得した**既存 Issue のタイトル一覧**（「既に Issue になっている課題は挙げない」と伝える）
- 引数の絞り込み条件

### 2-5. 所見のフォーマット（固定・§2-2 と §2-3 で共通）

1所見 = 1ブロック。これ以外を返さない。

```
### <所見の一言タイトル>
- カテゴリ: app | db | infra | measure
- 該当箇所: `webapp/go/livestream_handler.go:120-155 (getLivestreamsHandler)`
- 根拠: <計測数値・EXPLAIN・設定値・既存 index の有無。無ければ「未計測・要計測」>
- 対応方針: <2〜4行>
- 推定効果: 大 | 中 | 小（+ 一言）
- 推定コスト: 小 | 中 | 大（+ 一言）
- マニュアル上の懸念: <整合性・キャッシュ可否・禁止事項に触れうる点。無ければ「なし」>
- 触るファイル: `path`(修正) / `path`(新規) / `path`(設定)
- 未確認事項: <確認できなかったこと。無ければ「なし」>
```

## 3. 統合（直列・ここが精度のアンカー）

スキャナの所見が**全部返ってきてから**、§2-2 で本体が出した所見と合わせて、1回だけ判断する。
扱うのは生ファイルではなく圧縮済みの所見なので安い。

1. **重複を1件に畳む。** 共通ヘルパを複数の担当が挙げるのは正常。該当箇所が同じものは統合し、
   影響するエンドポイントを列挙する形にする（「この1箇所を直すと3エンドポイントが軽くなる」は優先度の根拠になる）
2. **同じ原因のものをまとめる。** 「index 不足」と「そのクエリの書き換え」が同じ変更で済むなら1 Issue にする
3. **既存 Issue と重複するものを落とす。** 既存 Issue で内容が薄いものは新規作成ではなくコメントで補足する方針を提案する
4. **マニュアル制約に反する候補をここで落とす。** 落とした理由は §7 で報告する
5. **粒度を揃える。** 1 Issue = 1 つの独立して着手・レビューできる変更。大きいものは分割する
6. **優先度を全カテゴリ横断で付ける。** **(期待効果 ÷ 実装コスト)** で決める。計測で上位に来ているものを high にする。
   ただし**マニュアル上加点されないエンドポイント**は、計測上位でも high にしない（理由を本文に書く）
7. **安定 ID を振る**（`A-01` app / `D-01` db / `I-01` infra / `M-01` measure）。
   **1 ID = 1 writer = 1 Issue**。これが二重作成を防ぐ唯一の仕組み
8. **触るファイル → ID のマトリクスを作り**、各 ID の競合相手（ID とタイトル）を確定させる

結果を `/tmp/isucon-issue-plan.md` に書き出す。writer への入力であり、失敗時の再開点でもある。

```md
## A-01
- タイトル: [App] GET /api/livestream 一覧取得のN+1クエリを一括取得に置き換える
- ラベル: category:app, priority:high
- 該当箇所: `webapp/go/livestream_handler.go:120-155 (getLivestreamsHandler)`
- 根拠: alp で sum 42.5s（全体の38%）/ ループ内で 1件ずつ SELECT / `livestream_tags` に index なし
- 対応方針: ...
- 期待効果: ...
- リスク: ...
- 触るファイル: `webapp/go/livestream_handler.go`(修正)
- 競合: 「[App] タグ取得の一括化」と `webapp/go/livestream_handler.go` で競合
- マニュアル根拠: 加点対象=... / 整合性=... / キャッシュ=... / 禁止事項=...
```

## 4. Issue 執筆＋作成（並列・1体 = 1 Issue）

`/tmp/isucon-issue-plan.md` の ID ごとに writer を起動する。**同時実行は最大5**
（`gh` の secondary rate limit を避けるため。件数が多い場合は5件ずつのバッチで回す）。

### 4-1. writer 共通の前置き

§2-4 の共通前置きをそのまま使い、末尾に次を足す。

```
追加で禁止:
- 割り当てられた ID 以外の Issue を作らない
- 与えられた優先度ラベルを変更しない
- ラベルを新規作成しない（既に作成済み）
- Issue 本文のテンプレートを改変しない（節の削除・追加・改名をしない）
```

### 4-2. 各 writer がやること

1. `/tmp/isucon-manual-notes.md` と `/tmp/isucon-facts.md` と
   `.claude/templates/isucon-issue.md` を **Read する**
2. 計画に書かれたパスと行番号を**自分で Read / Grep して再検証する**（スキャン結果を鵜呑みにしない）。
   ずれていたら実際の値に直す。存在しなければその行を落とし「未確認事項」として返す
3. `/tmp/isucon-issue-<ID>.md` に本文を書く。
   テンプレートの節を1つも欠かさず、末尾の `<!-- generated-by: /summarize-issues -->` を必ず入れる
4. Issue を作成する（`--dry-run` の場合はこの手順を飛ばす）:
   ```sh
   gh issue create --title "..." --body-file /tmp/isucon-issue-A-01.md \
     --label "category:app" --label "priority:high"
   ```
5. 次を返す:
   ```
   - ID: A-01
   - 番号: 42          （dry-run なら「未作成」）
   - URL: https://...  （dry-run なら「-」）
   - タイトル: ...
   - 影響ファイル: `webapp/go/livestream_handler.go:120-155`(修正) / ...
   - 未確認事項: なし
   ```

**Issue 本文のテンプレートと「影響ファイルの書き方（必須ルール）」は
`.claude/templates/isucon-issue.md` が唯一の正**。このコマンドに本文の雛形を再掲しない
（二重管理になると `/parallel-plan` が読めない Issue が生まれる）。

## 5. 作成結果の照合（省略しない）

並列作成では**失敗が静かに欠ける**。§6 に進む前に必ず照合する。

1. 計画した ID 全件に Issue 番号が付いているか突き合わせる
2. 欠けている ID は**その ID だけ直列で1回リトライ**する
3. それでも失敗したら、その ID を「未作成」として §7 に明記する（黙って落とさない）
4. 総数を GitHub 側からも確認する:
   ```sh
   gh issue list --state open --limit 200 \
     --search 'in:body "generated-by: /summarize-issues"' --json number,title | jq 'length'
   ```
5. `--dry-run` の場合は、`/tmp/isucon-issue-*.md` の数が計画 ID 数と一致することを確認する

個別 Issue を**すべて作成した後**に、まとめ Issue を 1 つ作る。

- タイトル: `[Dashboard] ISUCON 改善タスク一覧`
- ラベル: `dashboard`
- 本文構成:

```md

- 1 Issue = 1 PR。**`main` への push（＝PRマージ）で自動デプロイされる**（`.github/workflows/cd.yaml` は `push: branches: [main]` トリガー）。PR を作っただけでは反映されない
```

## 7. 最終報告

- **読んだマニュアルのパス** と、抽出できなかった項目
- マニュアルを根拠に**候補から外した改善案**（例: 「Redis 追加は禁止のためセッション移設は不可」）
- マニュアルを根拠に**優先度を下げた項目**（加点されないエンドポイントなど）
- 作成した Issue 数（カテゴリ別）と Dashboard Issue の URL
- 特に効果が大きいと判断した上位3件とその理由
- 情報不足で Issue にできなかった項目（例: ベンチ結果が無く判断不能なもの）と、それを埋めるために必要なもの
- **並列実行の結果**: §2-3 の担当分けと体数、§4 の体数、リトライした ID、
  **未作成のまま終わった ID**、スキャナ／writer が返した「未確認事項」の一覧

## 禁止事項

- **マニュアルを読まずに Issue を作らない**（見つからない場合は場所を聞いて中断する。例外は無い）
- **中断する場合はリポジトリにも GitHub にも何も書き込まない**（ラベル作成すらしない）
- **マニュアルで禁止されている変更を Issue にしない**
- マニュアルに書いていないことを「書いてある」ように引用しない。不明は「マニュアル要確認」と書く
- アプリケーションコードや設定ファイルを**修正しない**（このコマンドは課題の洗い出しと Issue 化のみ）
- 実物を読まずに一般論だけの Issue を作らない。該当箇所が示せない課題は Issue にしない
- 既存 Issue の重複を作らない
- Issue の一括クローズや既存 Issue の破壊的編集をしない
- **層（app / db / infra / measure）でスキャナを割らない。** 分量が釣り合わず短縮にならないうえ、
  index と呼び出し元を別々の担当が見ることになり、判断の質が落ちる（→ §2 の原則）
- **下地（§2-1）が無いままスキャナを起動しない**（index の有無を判定できない）
- **§2-3 のスキャナに Issue を作らせない**（二重作成の原因になる）
- **§4 の writer に優先度を決めさせない**（カテゴリ内だけの相対評価になる）
- **§5 の照合を省略しない**（並列化で失敗が静かに欠けるため、ここが唯一の検出手段）
- サブエージェントにさらにサブエージェントを起動させない
- **初期データの SQL dump を全読みしない**（数万行あり、時間だけ溶ける。DDL は grep で拾う）
